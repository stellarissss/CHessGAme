## 摘要

本项目实现了一套**规则可被自然语言实时改写的棋类游戏系统**。其核心不在于让语言模型下棋——恰恰相反，对局走法由传统搜索算法产生。本系统解决的问题是：如何把六种规则互异的棋类（中国象棋、围棋、五子棋、动物棋、跳棋、黑白棋）统一表示为**可由机器解释、可被机器修改的数据**，并在玩家用自然语言下达改写规则的指令后，于运行时刻完成"解析意图 → 生成配置补丁 → 校验 → 应用 → 热重建"的完整闭环，同时对这类改写行为施加一套可量化的代价与风险约束。

技术方案由九层构成：JSON 数据层（五类配置契约 + 不可变基线 + JSON Schema 约束）、规则解释层（五种移动原子 + 对称展开 + 条件表达式树 + 四级修饰符合并）、回合机制层（六个回合流程原语）、语言模型编排层（二级流水线 + 七类意图分类）、校验持久化层（RFC 6902 配置补丁 + 三层校验 + 错误驱动重试 + 撤回栈 + 热重建）、对局走法层（minimax / MCTS）、叙事进度层（语言模型作为裁判的业力评估 + 非线性识破概率模型 + 六道状态机 + 五级结局判定）、表现层（WebGPU 主通道与 melonJS 回退通道 + 设备自适应画质分级）、工程层（十二份同构部署拷贝 + 读写分离的配置缓存 + 基线差分成就检测）。

本文全部技术断言均标注了源文件与行号，可逐条核验。凡未实现或与设计书存在偏差之处，均在 §6 与各分册第 6 节如实说明，不作粉饰。

## 1 背景与问题定义

### 1.1 问题

传统棋类电子游戏把规则编写在程序代码里。一处规则要改，就要改代码、重新编译、重新发版。这带来三个后果：

1. **规则不可塑**。玩家任何玩法设想都必须由开发者预先实现。
2. **多棋种无法复用**。象棋的马的走法与围棋的提子规则无法共用同一套表示，六个棋种就要写六套规则代码。
3. **改写不可控**。即便开放了修改通道，也缺少对"改了多少、代价多大、是否会被系统识破"的统一量化方式。

### 1.2 本项目的目标

1. 把六棋种的规则、棋盘、棋子、状态、界面全部表达为**数据**（JSON），由统一的词汇表描述，使同一套解释机制可以处理所有棋种。
2. 让玩家用**自然语言**下发改写指令，由语言模型产出标准格式的**配置补丁**（RFC 6902 JSON Patch），经多重校验后在运行时刻应用，无需重启。
3. 对上述改写行为建立**可量化的代价模型**（业力值与识破概率），使"作弊"成为一种有风险的资源消耗决策，而非无条件特权。
4. 保证对局本身的棋力与语言模型解耦：即使在无语言模型、无网络、无密钥的情况下，对局仍可正常运行。

### 1.3 一个必须澄清的定性（关键）

**本系统不使用语言模型选择走法。** 这一点常被误读，在此明确：

| 环节 | 实现 | 是否依赖语言模型 |
|:---|:---|:---:|
| 走法搜索 | 象棋、黑白棋：minimax；围棋：MCTS | 否 |
| 走法合法性 | 规则引擎枚举合法走法集合，搜索只在该集合内进行 | 否 |
| 自定义棋子估值 | 象棋：语言模型返回整数分值，并有查表式启发式兜底 | 是（可降级）|
| 规则改写 | 二级语言模型流水线产出配置补丁 | 是（核心）|
| 作弊代价评估 | 语言模型作为裁判输出业障整数，并有静态价目表兜底 | 是（可降级）|

无 API 密钥时，系统走启发式估值与静态价目表，为此 AI 功能降级但不会被判负。相关代码：`xiangqi/chess_ai.py:349-350`（无密钥直接转启发式）、`:435-483`（异常兜底与查表估值）、`shared/karma_assessor_base.py:270-279`（静态价目表）。

## 3 关键设计取舍

**取舍一：为什么不用语言模型选走法。**
语言模型的采样不确定性会让同一局面走出不同着法，且响应延迟（本项目单次请求超时上限 120 秒）远高于搜索算法。把对局走法交给 minimax / MCTS，可以让"AI 功能降级"不影响棋局的基本可玩性——这是把语言模型限定在"规则改写"而非"参与决策"的直接理由。

**取舍二：为什么用配置补丁而不是重新生成整份配置。**
`xiangqi/无限制象棋_完整计划书_v4.0.md:65` 给出的理由是减少 token 消耗与出错概率。代价是需要额外实现一条"抽取失败则退化为全量 JSON 再反向生成补丁"的兼容路径（`ai_orchestrator_base.py:822-830`）。

**取舍三：为什么改用 WebGPU 主通道 + 回退通道的双渲染通道。**
见 §2.2 表现层。这里只补充一点工程判断：回退的判断条件是**明确报错**（无 WebGPU、初始化异常、适配器缺失、设备丢失），而不是"画面看起来不对"。呈现自检默认只打告警角标，不自动降级；需显式加 `?owselfcheck=1` 才会启用破坏性降级。这个默认值选择是刻意的——避免一次误判把可用画面葬送掉。

**取舍四：为什么保留十二份近乎重复的实现拷贝。**
`shared/mechanism_engine_base.py:5-10` 记录了抽取过程：顶层六份实现经 difflib 量化平均相似度 96.4%，随后抽出公共基类；沙盒副本与顶层同名文件 100% 相同。这是渐进式重构的中间状态，而非设计选择——见 §6。

## 6 已知局限与已修正的事实偏差

防御性公开文档的可信度取决于是否如实交代缺陷。以下几项在撰写过程中经复核修正，与原设计书或早期描述不一致，**以源码为准**：

1. **`has_property` 谓词未实现**。计划书 `xiangqi/无限制象棋_完整计划书_v4.0.md` 的 where 条件表中列入了该谓词，但全项目源码无对应实现分支。已核实：全仓 `.py` / `.json` 检索无命中。分册 01 已剔除该谓词。
2. **胜负条件开关并非全部生效**。计划书 `:764`、`:806` 自承"胜利条件和特殊规则仍由规则引擎硬编码，未实现完全数据驱动"。实测分三档：动物棋 `check_win`(:784-833) 确实读取 `win_conditions.enter_den.enabled`；围棋确实读取 `ko_rule` / `suicide_rule` / `forbidden_black` 的 `enabled`；**象棋的 `is_checkmate`(:593) 与 `is_general_captured`(:621) 不读 `rules.json`**。
3. **Schema 契约存在未暴露的多处冲突**。黑白棋 `ai_difficulty.levels` 为 `easy/normal/hard/master`、`current` 为 `"normal"`，而 `shared/schemas/rules.schema.json` 规定 `current` 枚举为 `easy/medium/hard`；黑白棋每条 `win_conditions` 条目的 `category` 为 `"standard"`，越出 `shared/schemas/rules.schema.json:24` 的 `victory/draw/special` 枚举；`pieces.schema.json:10` 的 `side` 枚举为 `red/black`，而黑白棋 `pieces_white.json` 顶层 `side` 为 `white`。由于 `game_base.py:342 load_configs()` **不执行 Schema 校验**，这些冲突在运行时不报错，处于潜伏状态。
4. **Schema 校验的覆盖面有限**。唯一的自动调用点在 `ai_orchestrator_base.py:2834`（人工智能生成配置后的重试循环内）。普通配置加载路径不做校验。
5. **被识破后的实现与设计书不一致**。设计书称"业力锁死为 0"，但 `samsara/state.py:518-530` 的 `reset_on_detection` 只锁死 `realm_detections` 与 `detection_state`，**从未对 `level_karma` 赋值 0**。
6. **结局判定条件比设计书更严格**。`samsara/endings.py:99-166` 中，除 `exposed` 外的四个结局均额外要求 `prayer_count == 0`，即一旦祈求过就只能走 `exposed` 分支。
7. **提示词常量的真实命名**为 `INTENT_PARSER_SYSTEM` / `RULE_MODIFIER_SYSTEM` 等，均带 `_SYSTEM` 后缀，编排器通过 `_get_prompt("INTENT_PARSER_SYSTEM")` 取用；早期内部简报曾略去后缀，已在分册 04、05 中更正。
8. **B+C 复合分类无专属处理器**。意图层会把复合请求拆成多条独立 action 顺序执行，编排器侧没有合并处理器。
9. **十二份重复拷贝是工程债**。具体差异：`prompts.py` 与 `chess_ai.py` 在六个棋种中的五个于主目录与沙盒间逐字节相同，但**动物棋两者存在差异**（主目录版含"陷阱重构为地形棋子原语 `category:"terrain"`"，沙盒版缺省）；`rule_engine.py` 的差异是沙盒版缺少 O(1) 位置索引 `_pos_index`，属性能差异而非功能差异。
10. **成就定义双份硬编码**。Python 版在顶层 `main.py:148-195`（37 条，含 4 条元成就）；JS 版在 `shared/achievement_checker.js:31-69`，仅含 `name/icon/desc`，缺 `category/rarity/games` 字段，两者仅靠注释约定同步，无自动一致性校验。
11. **语言模型输出非结构化解码**。无论配置补丁还是业障整数，都依赖"提示词声明 + 后处理抽取/强转"，未使用 constrained decoding。这是三层校验与静态价目表兜底存在的直接原因。
