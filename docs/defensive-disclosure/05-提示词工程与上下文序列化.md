# 提示词工程与上下文序列化

## 摘要

两级流水线能否产出可用的配置补丁，取决于第一级与第二级的提示词如何组织，以及向模型注入多少、何种形式的棋局上下文。本分册记录本项目提示词的组装方式（系统提示词 = 角色句 + 拼接的 primer 常量，用户提示词由基类动态拼装）、输出约束的实现方式（提示词声明 + 后处理抽取，而非结构化解码），以及三类上下文序列化策略：意图层只注入文字摘要、黑白棋覆盖版注入 ASCII 矩阵、代码生成层注入完整配置 JSON。同时记录"已激活规则"如何在下一轮意图提示词中回灌，形成规则描述与意图解析之间的反馈回路。本文所有技术断言均可由所列 `文件:行号` 复核。

## 1 背景与问题定义

让大语言模型改写棋类配置，面临两个约束：其一，模型必须按本项目自定的原语词汇（见分册 01）与 JSON 结构输出，否则补丁无法被引擎解释；其二，模型需要足够但不过量的棋局上下文——过少则改错目标，过多则浪费 `max_tokens` 且引入噪声。

由此要回答的问题：系统提示词如何稳定地"教会"模型本项目的词汇与输出格式；用户提示词如何随任务动态注入上下文；上下文的"量"按阶段如何取舍。

## 2 相关做法与本方案的区别

少样本（few-shot）提示词通常提供若干"输入—输出"样例对来校准模型。本项目的示例不是严格 few-shot 问答对，而是"完整示例 JSON"——直接给出期望输出的整段结构示例（如黑白棋 6 个完整示例、象棋 7 个 A 类完整示例），让模型参照结构而非模仿语义。这与逐条 few-shot 不同，更接近"结构模板示范"。

另一类做法是把整份配置始终塞进上下文。本项目按阶段区分：意图层只给摘要，代码生成层才给完整配置。这种分级注入降低了意图解析阶段对 `max_tokens` 的压力，也避免把无关棋子的完整规则暴露给第一级模型。

输出格式约束方面，许多系统采用 constrained decoding（如 grammar-constrained sampling）强制合法 JSON。本项目未采用该方式，而是提示词声明 + 后处理抽取，代价是存在解析失败概率，需以重试与校验兜底（见分册 06）。

## 3 技术方案

### 3.1 系统提示词组装

系统提示词采用"角色句 + primer 常量拼接"的静态结构。以象棋为例，`INTENT_PARSER_SYSTEM`（`xiangqi/prompts.py:205`）以角色句开头，随后依次拼接 `PIECE_TYPE_MAP + PIECE_NAME_MAP + PIECE_PRIMITIVE_PRIMER + ATOMIC_CAPTURE_MODIFIERS`（`:209-213`），再展开分类体系说明。primer 常量承载原语词汇与原子吃子修饰器的定义，使模型在解析意图时已掌握本项目的"词汇表"。

用户提示词不硬编码，而是由编排器基类按任务动态拼装：意图层拼入棋局摘要与已激活规则（见 4.2），代码生成层拼入任务说明、参数、约束与完整配置（见 4.3）。

### 3.2 输出约束方式

第一级与第二级均不依赖结构化解码。系统提示词在 primer 中声明优先输出 RFC 6902 Patch 数组并"只输出 JSON"（如 `JSON_PATCH_PRIMER`，`xiangqi/prompts.py:9-24`），代码侧再用 `_extract_json`（`shared/ai_orchestrator_base.py:725`）与 `_extract_json_patch`（`:755`）从模型文本中抽取 JSON 或 Patch 列表。抽取失败即触发重试与校验（见分册 06）。

### 3.3 上下文序列化的三种策略

| 阶段 | 注入形式 | 内容 |
|:--|:--|:--|
| 意图层（基类） | 文字摘要 | 当前回合 + 阵营存活子数 + 逐子位置 |
| 意图层（黑白棋覆盖版） | ASCII 矩阵 | 8×8 棋盘字符图 + 行列号 + 棋子统计 + 合法落子点 |
| 代码生成层 | 完整配置 JSON | 目标配置文件的 `json.dumps(..., indent=2)` 全量内容 |

### 3.4 规则描述与意图解析的反馈回路

C 类修改成功后，系统把"动作描述字符串"追加进 `board_state.game_status.custom_rules_active`（`:1948-1954`）；下一轮意图提示词在 `:1154` 读取该列表，于 `:1161` 注入"已激活的自定义规则：…"。黑白棋版以 `extra` 变量完成同样回灌（`heibaiqi/ai_orchestrator.py:226-230`）。需明确：回灌的是动作描述字符串，不是 `rules.json` 全文。

## 4 本项目实现

### 4.1 系统提示词常量（实际命名）

经源码核对，象棋版常量名均带 `_SYSTEM` 后缀（与 `shared/ai_orchestrator_base.py:633` 的 `_get_prompt` 用 `getattr` 取用一致）：

- `INTENT_PARSER_SYSTEM`（`xiangqi/prompts.py:205`）：拼接 `PIECE_TYPE_MAP`、`PIECE_NAME_MAP`、`PIECE_PRIMITIVE_PRIMER`（`:60-172`）、`ATOMIC_CAPTURE_MODIFIERS`（`:175-198`）；
- `RULE_MODIFIER_SYSTEM`（`:721`）、`BOARD_TRANSFORMER_SYSTEM`（`:823`）、`UI_MODIFIER_SYSTEM`（`:925`）、`FUN_RESPONSE_SYSTEM`（`:1018`）、`PIECE_CREATOR_SYSTEM`（`:1034`）、`MECHANISM_MODIFIER_SYSTEM`（`:1234`）；
- 规则原语 primer：`JSON_PATCH_PRIMER`（`:9-24`）声明 RFC 6902 与 op 取值（add/remove/replace 等）。

各棋种 primer 侧重不同：

- 围棋 `GO_RULE_PRIMER`（`weiqi/prompts.py:40-72`）讲解 `ko_rule`（打劫）、`suicide_rule`（自杀）、`forbidden_black`（黑棋禁手）、`liberty_cap`（限气）、`uncapturable`（不可吃）等围棋专用规则与机制原语；
- 黑白棋 `PIECE_PRIMITIVE_PRIMER`（`heibaiqi/prompts.py:48-124`）定义 `jump` / `ray` / `flip` 三原子，其中 `flip`（夹吃翻转）在 `:80-93` 详述。

### 4.2 意图层上下文（文字摘要与 ASCII 矩阵）

基类意图提示词在 `shared/ai_orchestrator_base.py:1156-1170` 组装：当前回合（`:1157`）、`_get_board_summary` 给出的阵营存活子数（`:1158`，实现见 `:1196-1204`，形如"红方N子, 黑方M子"）、`_build_game_insight` 给出的逐子 `名@(x,y)` 实况（`:1160`，实现 `:1206-1241`）、以及已激活规则（`:1161`）。

黑白棋覆盖版改写上下文来源：其 `_get_board_summary`（`heibaiqi/ai_orchestrator.py:73`）构建 8×8 ASCII 矩阵（`:86-152`），用 `●`/`○`/`.` 表示黑/白/空，附行列号、棋子统计与合法落子点（`:140-146`）；`_parse_intent_with_log`（`:219`）在 `:225` 取该摘要、在 `:226-230` 以 `extra` 追加已激活规则。

### 4.3 代码生成层上下文（完整配置 JSON）

C 类处理函数在组装用户提示词时，把目标配置全量注入：`:1916-1919` 以 `json.dumps(pieces, ensure_ascii=False, indent=2)` 输出 `pieces` 完整内容（代码位于 `shared/ai_orchestrator_base.py` 的 C 类处理函数内，紧邻 `:1930` 的 `_call_code_ai_with_validation` 调用）。同段提示词要求"优先输出 JSON Patch 数组（RFC 6902 格式）"，末尾声明"只输出JSON"（`:1922-1929`）。

### 4.4 完整示例（结构模板示范）

本项目以"完整示例 JSON"而非严格 few-shot 问答对来示范输出结构：

- 象棋 A 类示例 1–7，覆盖悔棋、判胜、认输、改 AI 性格、冻结 AI、AI 接管、自定义性格，位于 `xiangqi/prompts.py:524-700`（示例 6 见 `:643`，示例 7 见 `:670`）；其中含 `confidence` 字段（`:642`）。
- 黑白棋 6 个完整示例，覆盖悔棋、AI 接管、改 flip 距离、建跳吃子、改 10×10 棋盘、搞笑请求，位于 `heibaiqi/prompts.py:285-360`。该版意图输出示例（`:255-281`）不含 `confidence`，与上一点如实对照。

### 4.5 输出抽取函数

- `_extract_json`（`shared/ai_orchestrator_base.py:725`）：优先 `json.loads` 整段，失败则正则抽取 ```json 代码块，再失败则取首个 `{` 到末 `}`。
- `_extract_json_patch`（`shared/ai_orchestrator_base.py:755`）：抽取 JSON Patch 数组（顶层为 list），同样支持代码块与括号定位回退。

## 5 验证情况

本文结论基于源码静态核查：已核对系统提示词常量命名、primer 行号、意图层与代码生成层的上下文注入点、ASCII 矩阵构造、完整示例位置与抽取函数。端到端提示词效果（真实模型输出质量、不同指令下的解析成功率）未做系统化评估，本文不作"已验证有效"声明；本节仅确认上述提示词与注入逻辑在代码中确实存在并按描述组织。

## 6 局限性

- **输出约束非结构化解码**：依赖"提示词声明 + 后处理抽取"，存在解析失败概率，需以三层校验与重试兜底（见分册 06）。这不是严格保证合法输出的机制。
- **意图输出结构跨棋种不一致**：象棋示例含 `confidence`（`xiangqi/prompts.py:642`），而黑白棋意图输出示例（`heibaiqi/prompts.py:255-281`）不含该字段，两者字段集合不同，下游若依赖 `confidence` 需按棋种区分。
- **primer 与示例为各棋种独立维护**：6 个棋种各自的 `prompts.py` 对同一类原语（如移动原语）分别定义，存在表达不一致与维护冗余的风险。
- **完整配置注入占用 token**：代码生成层注入全量配置（`:1916-1919`），对大配置文件会逼近 `max_tokens=8192` 上限，长指令延迟明显。
