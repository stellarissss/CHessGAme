# 棋类规则原语化与移动原子体系

## 摘要

本项目把 6 种棋类（象棋、围棋、五子棋、动物棋、跳棋、黑白棋）的棋子走法拆解为一组有限的移动原语（`jump` / `ray` / `flip` / `step` / `hop`），配合对称展开（`sym`）与条件表达式树（`where`），用 JSON 描述每一种棋子的全部合法走法。本分册记录这套原语词汇表、条件表达式的语法，以及它们在本项目各棋种配置与引擎中的具体落点。本文所有技术断言均可由所列 `文件:行号` 或配置片段复核。

## 1 背景与问题定义

在传统棋类程序中，每种棋的走法通常写死在各自引擎的分支逻辑里：新增或改写一种走法需要直接改动代码。本项目把"走法"从代码下沉为数据，使规则可由外部（含大语言模型流水线）直接改写，而不必修改引擎的解释逻辑。

由此产生的问题：如何用一组有限的词汇覆盖差异极大的走法？例如象棋马的蹩腿、炮的隔子吃、象的塞眼；黑白棋的夹吃翻面；跳棋的连续跳越；动物棋的等级吃与跳河。本项目给出的答案是把走法分解为"原语 + 对称 + 条件"三层，引擎只解释执行，不直接编码任何具体棋子的走法。

## 2 相关做法与本方案的区别

国际象棋类引擎常用"每子一个生成函数"或预生成攻击位掩码（如 magic bitboard），与具体棋种强耦合，走法数据与引擎逻辑混在一起。FEN、XGN 等标准只描述局面快照，并不描述走法规则本身。

本方案不同之处：走法规则本身也成为数据。引擎只认识原语词汇表与条件表达式，不内置任何具体棋子的走法；同一套词汇表通过各自独立的引擎解释执行，覆盖全部棋种。

## 3 技术方案

### 3.1 原语枚举

- **`jump`（离散跳跃）**：`to` 为相对偏移 `[dx,dy]` 或 `"$forward"`；`block` 为关卡格列表，起跳前这些格子必须为空（如马腿 `[0,1]`、象眼 `[1,1]`）；`land` 为落点要求，取值 `empty` / `enemy` / `any`。
- **`ray`（射线滑行）**：`dir` 为方向向量；`max` 为最大步数（`-1` 表示无限）；`screens` 为需跳过的棋子数（`0` 表示空走可落，`1` 表示须隔一子方可吃）；`land`；`sym`。
- **`flip`（夹吃翻转，黑白棋专有）**：沿 `dir` 从落子点先遇不少于 1 枚敌子、再遇 1 枚己子，中间敌子翻转为己方。
- **`step`（跳棋单步）**、**`hop`（跳棋连跳，`chain:true`）**：落点要求 `empty`。

### 3.2 对称展开 `sym`

取值：`none` / `rotate4` / `rotate4_mirror` / `mirror_x`；跳棋额外使用 `hex6`（六边形六向）。引擎在运行时把单条 move 定义按 `sym` 展开为多条具体方向。以 `rotate4` 为例，对 `jump` 的 `to` 与 `block` 做 90° 整数旋转得到四个方向；`rotate4_mirror` 在此基础上再对 y 分量取反。

### 3.3 条件表达式树 `where`

谓词（已在代码中核实）：`in_region` / `crossed_river` / `same_side` / `at_row` / `at_col` / `not` / `and` / `or`；动物棋扩展 `in_water` / `in_trap` / `in_enemy_trap` / `in_own_den` / `in_enemy_den`（见 `dongwuqi/rule_engine.py:684-702`）。

位置变量：`$self`（棋子当前位置）、`$dest`（目标格）、`$side`、`$palace`、`$forward`（仅作为 `to` 的取值，红方 `[0,-1]`、黑方 `[0,1]`）；`$opponent` 仅在跳棋引擎中出现。

补充说明：计划书中曾把 `has_property` 列入谓词，但全部引擎源码中均无对应分支，本方案当前并不支持该谓词，本文如实不收录。

### 3.4 派生原语

- **吃子原语 `capture`**：`mode ∈ {rank_ge, any_enemy, rank_le}`，用于动物棋等级吃（`dongwuqi/schemas/pieces.schema.json:192-193`：`rank_ge` 攻击方等级≥防守方可吃，`any_enemy` 任意敌方可吃，`rank_le` 反向）。
- **地形棋子**：`category:"terrain"` 配合 `effects:[{type:"rank_override", target, scope:"while_occupying"}]`（陷阱使进入者等级被覆盖，见 `dongwuqi/configs/pieces_red.json:397,417`）。
- **路径约束 `path_constraint`**：`{must_be:"water"|"land"|"any"}`，用于动物棋狮虎跳河（`dongwuqi/configs/pieces_red.json:94-95`）。

### 3.5 结构示例（象棋马）

```
{
  "kind": "jump",
  "to":   [1, 2],
  "block": [[0, 1]],   // 马腿：起跳前此格不得有子
  "land": "any",
  "sym":  "rotate4_mirror"
}
```

引擎解释流程（以象棋为例）：

```
get_valid_moves(piece)                  // xiangqi/rule_engine.py:33
  for move_def in 棋子.moves:
      for exp in _expand_symmetry(move_def):   // :181  按 sym 展开方向
          moves += _execute_move_def(exp)      // :243
              ├─ _jump_moves(exp)              // :254  查 block 关卡 → 判 land
              └─ _ray_moves(exp)               // :322  按 screens/land 滑行
      all_moves = _restrict_captures(...)      // :164  按 can_capture/eatable 过滤
```

## 4 本项目实现（证据）

- 象棋全部走法写在 `xiangqi/configs/pieces_red.json`：将、士用 `jump` + `where:[{in_region:{pos:"$dest",region:"$palace"}}]` 限制九宫；象用 `jump` + `block:[[1,1]]`（象眼）+ `where:[{not:{crossed_river:{pos:"$dest"}}}]`；马用 `jump` + `block:[[0,1]]`；车、炮用 `ray`（炮 `screens:0` 空走、`screens:1` 隔子吃）；兵用 `jump` `to:"$forward"` 与 `mirror_x` 过河横移。
- 黑白棋 `flip` 原语：`heibaiqi/configs/pieces_black.json` 中 `disc` 的 `moves` 含 `{"kind":"flip","dir":[1,0],"max":6,"land":"enemy","sym":"rotate4_mirror"}`；`heibaiqi/rule_engine.py:5-12` 自述"三原语：jump/ray/flip"。
- 跳棋 `step`/`hop`：`tiaoqi/configs/pieces_red.json` 中 `piece` 的 `moves` 含 `{"kind":"step","land":"empty","sym":"hex6"}` 与 `{"kind":"hop","land":"empty","chain":true,"sym":"hex6"}`。
- 执行路径：`xiangqi/rule_engine.py` 的 `get_valid_moves`（`:33`）对每条 move 定义依次调用 `_expand_symmetry`（`:181`）、`_execute_move_def`（`:243`），分派至 `_jump_moves`（`:254`）与 `_ray_moves`（`:322`）；`_ray_moves` 依据 `screens` 与 `land` 计算可落点，`_jump_moves` 先查 `block` 关卡格再判 `land`。
- 命名佐证：`xiangqi/无限制象棋_完整计划书_v4.0.md:56` 称"jump/ray 双原子移动体系"，`:64` 与 `:215` 称"jump + ray 两种原子移动原语"。

## 5 验证情况

已通过阅读源码与配置确认：上述原语词汇在各棋种 `pieces_*.json` 与对应 `rule_engine` 中均有对应字段与解释执行路径（象棋 `_jump_moves`/`_ray_moves`、黑白棋 `flip`、跳棋 `step`/`hop`）。

逐原语、逐棋种的自动化单元测试未在本项目内做系统化回归，本文不作"已验证"声明；本节结论仅基于静态代码与配置核查。

## 6 局限性

- `has_property` 谓词在计划书中被提及，但引擎源码无对应实现，当前 `where` 表达式不支持该谓词。
- `$opponent` 变量仅在跳棋引擎中出现，并非全部引擎通用。
- 原语词汇虽统一，但解释逻辑分散在 12 份各自独立的 `rule_engine` 拷贝中（见分册 03），同一原语的边界处理（越界、索引方式）在不同棋种间未必完全一致。
- 所有走法均为解释执行，无编译期走法生成或优化产物。
