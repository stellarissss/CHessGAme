# 多棋种同构部署与配置缓存架构

## 摘要

本分册记录「棋圣·六道轮回」在六个棋种上采用的同构部署形态，以及支撑「AI 实时改写规则」的配置缓存架构。核心事实：六个棋种各有一套完整主目录，并在 `sandbox/` 下各有一套纯净模式副本，合计十二份同源实现；这些拷贝经由 `shared/` 下的基类抽取部分去重，但仍存在大面积逐字节重复，是明确的技术债。对局与 AI 计算所需的规则 / 棋子 / 棋盘配置以原子化配置形式常驻内存缓存，仅在对局、合法移动计算与 AI 落子时读取缓存，仅在 AI 修改成功应用或重置 / 重开 / 关卡切换时整体重载一次。所有断言均指向 `文件:行号`，复核中发现的与立项简报不符之处在第 6 节如实列出。

## 1 背景与问题定义

项目有六个棋种：xiangqi（象棋）、weiqi（围棋）、wuziqi（五子棋）、dongwuqi（动物棋）、tiaoqi（跳棋）、heibaiqi（黑白棋）。每个棋种都有「用大语言模型把棋盘 / 棋子 / 规则 / 机制改写成任意形态」的能力，且改写由原子化配置驱动——规则、棋子、棋盘都被拆成可独立 patch 的 JSON 文件。

带来的工程问题是：六套棋类的引擎与编排代码高度同构，如何在保证各棋种可独立演化的同时避免无意义的重复；以及，AI 每次改写后若都从磁盘重新读取全部配置，会在对局与合法移动计算的热点路径上产生大量重复 IO，需要一套「读一次、常驻内存、必要时整体重载」的缓存策略。

## 2 相关做法与本方案的区别

通用做法是「一个引擎 + 多套数据」或「一份配置 + 多份规则数据」。本项目的区别是：六套棋类各自保留完整可独立运行的代码拷贝（含 `main.py`、`prompts.py`、`chess_ai.py`、`rule_engine.py`、`mechanism_engine.py` 与各自的 `configs/`），并在 `shared/` 中抽取出少量真正公共的基类与路由注册函数。这是「先各自实现、再抽取公共部分」的折中，而非一开始就做单引擎抽象。

在配置访问上，本项目不采用「每次操作都重新加载」或「按需懒加载单文件」的方案，而是显式维护一个 `_config_cache_valid` 标志：缓存有效时 `load_configs` 直接复用内存中的 `self.configs`，缓存失效时才重新读盘并在随后热重建引擎（`shared/game_base.py:342-355`）。

## 3 技术方案

### 3.1 同构部署形态

十二份拷贝的构成：六个棋种主目录 `xiangqi / weiqi / wuziqi / dongwuqi / tiaoqi / heibaiqi`，以及 `sandbox/` 下对应的六个子目录 `sandbox/xiangqi … sandbox/heibaiqi`。每份拷贝都含 `main.py`、`prompts.py`、`chess_ai.py`、`rule_engine.py`、`mechanism_engine.py` 与 `configs/`。

主目录版与沙盒版的关键差异（以 heibaiqi 为代表逐文件 `diff -q` 核实）：

- `prompts.py`、`chess_ai.py`：在 xiangqi / weiqi / wuziqi / tiaoqi / heibaiqi 五组里主目录与沙盒版逐字节相同（`diff -q` 无输出）。
- `dongwuqi` 例外：其主目录版 `prompts.py` 与 `chess_ai.py` 相比沙盒版多出了「陷阱重构为地形棋子原语（category="terrain"）」的实现，二者并不相同（详见第 6 节）。
- `rule_engine.py`：主目录版含有 O(1) 位置索引 `_pos_index`（六个棋种主目录版 grep 命中 2–4 处），沙盒版全部缺失该索引（grep 命中 0 处）；属性能差异，非功能差异。
- `main.py`：差异最大。主目录版 `class GameState(BaseGameState)` 继承 `shared/game_base.BaseGameState`，并通过 `register_common_routes` 注册通用路由（`heibaiqi/main.py:37-38, 67, 232`）；沙盒版是重构前的单体 `class GameState`，自带 `load_configs` / `save_config` / `apply_config_update` / `undo_stack` / `reset_board`（`sandbox/heibaiqi/main.py:45-147`）。

主目录版与沙盒版在编排器基类上也不同：主目录版 `AIOrchestrator` 继承 `RPGOrchestratorBase`（带 `karma_assessor`），沙盒版继承 `AIOrchestratorBase`（无 karma）（`heibaiqi/ai_orchestrator.py:16-23` 与 `sandbox/heibaiqi/ai_orchestrator.py:16-22`）。

业务语义上，沙盒是「剥离 karma / 关卡约束的自由练习场」（纯净模式），其「无限制改规则」能力本体与主目录同源——二者共用同一套 `rule_engine` / `chess_ai` / `prompts` 逻辑，只是沙盒不接入 samsara 的业力与技能体系。

### 3.2 配置缓存策略

原子化配置以文件名列表声明（`shared/game_base.py:241-243`）：

```python
CONFIG_FILES = ["board_state", "board", "pieces_red", "pieces_black", "rules", "ui_config"]
```

缓存由实例字段 `_config_cache_valid`（`shared/game_base.py:261`）控制。各方法职责：

- `load_configs`（`shared/game_base.py:342-355`）：仅当 `_config_cache_valid` 为 False 时，遍历 `CONFIG_FILES` 逐个 `json.load` 进 `self.configs`，随后置缓存有效并重热重建引擎。**该函数不做 schema 校验，只做 `json.load`**。
- `invalidate_config_cache`（`shared/game_base.py:357-359`）：把 `_config_cache_valid` 置 False，使下一次 `load_configs` 重新读盘。
- `save_config`（`shared/game_base.py:365-369`）：把单个配置写回对应 JSON 文件。
- `apply_config_update`（`shared/game_base.py:376-393`）：先对将被修改的配置做深拷贝快照并压入 `undo_stack`（上限 10，超出丢弃最旧，见 384-386 行），再替换内存配置、落盘、标记缓存有效、热重建引擎。
- `undo_last_config_change`（`shared/game_base.py:395-405`）：弹出最近快照恢复配置，落盘并重热重建。
- `_rebuild_engines`（`shared/game_base.py:275-280`）：抽象方法，由子类重建 RuleEngine / ChessAI / MechanismEngine；未实现则抛 `NotImplementedError`。
- `reset_board`（`shared/game_base.py:407-423`）：从 `configs/initial/*.json.initial` 还原点重新加载全部配置，清空撤回栈，标记缓存有效，热重建引擎，落盘并调用 `_after_reset_board` 钩子。

策略归纳：对局、合法移动计算与 AI 落子三个阶段只读取内存中的 `self.configs`，不逐次读盘；只有当 AI 对配置的修改成功应用（`apply_config_update`）、或执行重置 / 重开 / 关卡切换（`invalidate_config_cache` 或 `reset_board`）时，才整体重载一次。

### 3.3 不可变基线与活配置

`configs/initial/*.json.initial` 是出厂还原点（还原点），由 `reset_board` 读取；`configs/*.json` 是当前可被 AI / 玩家 patch 污染的活配置。二者路径分离，使「还原到出厂规则」与「在活配置上累积改动」互不干扰。

### 3.4 基类抽取

`shared/mechanism_engine_base.py:5-10` 的注释自述：十二份 `mechanism_engine.py`（六主目录 + 六沙盒）经 difflib 量化，顶层六份平均相似度 96.4%，且沙盒副本与顶层同名文件 100% 相同（diff 为 0），据此抽出 `MechanismEngineBase`。这是同构重复架构的直接证据，也标定了未抽取部分仍是工程债。

## 4 本项目实现

- 十二份拷贝的目录存在性：主目录 `xiangqi weiqi wuziqi dongwuqi tiaoqi heibaiqi` 与沙盒 `sandbox/{xiangqi,weiqi,wuziqi,dongwuqi,tiaoqi,heibaiqi}`（目录清单经 `ls -d` 核实）。
- 主目录 / 沙盒 `prompts.py`、`chess_ai.py` 逐字节相同：xiangqi / weiqi / wuziqi / tiaoqi / heibaiqi 五组 `diff -q` 无差异；dongwuqi 两组有差异（第 6 节）。
- 主目录 / 沙盒 `rule_engine.py` 差异：`_pos_index` 主目录版 2–4 处、沙盒版 0 处（六棋种 grep 一致）。
- 主目录 `main.py` 继承 `BaseGameState` 并 `register_common_routes`：`heibaiqi/main.py:37-38, 67, 232`；沙盒 `main.py` 为单体 `GameState` 且自带配置方法：`sandbox/heibaiqi/main.py:45-147`。
- 编排器基类差异：主目录 `RPGOrchestratorBase`，沙盒 `AIOrchestratorBase`：`heibaiqi/ai_orchestrator.py:16-23` 与 `sandbox/heibaiqi/ai_orchestrator.py:16-22`。
- 主目录 `/api/command` 拉取 samsara 的 `skill_modifiers` / `allowed_classifications`，做 karma 增减与透支判定，并同步 `/api/karma/consume`、`/api/cheat/record`：`xiangqi/main.py:152-262`（其中 178-180 拉取修饰符，211-241 增业力并同步 consume / cheat/record）。沙盒版 `/api/command` 存在但无上述 karma 钩子（grep 在 `sandbox/heibaiqi/main.py` 中查不到 `skill_modifiers` / `allowed_classifications` / `/api/karma/consume` / `/api/cheat/record`）。
- 配置缓存方法：`shared/game_base.py:241-243, 261, 275-280, 342-355, 357-359, 365-369, 376-393, 395-405, 407-423`。
- 不可变基线：`shared/game_base.py:407-417`（`reset_board` 从 `configs/initial/*.json.initial` 读取）。
- 基类抽取注释：`shared/mechanism_engine_base.py:5-10`。

### 4.1 成就系统

成就定义不是配置驱动，而是两份硬编码副本：

- Python 副本：`main.py:148-195` 的 `ACHIEVEMENT_DEFINITIONS`，每条含 `id / name / desc / icon / category / rarity / games` 字段，共 37 条（其中 4 条为 meta 元成就：samsara / collector / completionist / pokedex，见 `main.py:191-194`）。
- JS 副本：`shared/achievement_checker.js:31-69` 的 `ACHIEVEMENTS`，仅含 `name / icon / desc`，其文件注释 `// 成就定义（与 main.py ACHIEVEMENT_DEFINITIONS 同步）`（第 30 行）标明需与 Python 副本保持一致，但靠人工注释约束，无自动校验。

触发机制是基线差分（baseline diff）。前端 `checkAfterConfigLoad`（`shared/achievement_checker.js:131` 起）在配置加载后比对 `_baseline` 的 `bgColor / lineColor / geometry（宽高）/ custom_pieces` 是否相对基线发生变化（基线建立于 135-139 行，比对逻辑 146-181 行），一旦变化即 `POST /api/achievements/unlock`（`shared/achievement_checker.js:84`），后端 `_check_meta_achievements`（`main.py:223-256`）据已解锁数判定元成就：collector ≥ 10、completionist ≥ 25、samsara = 六个棋种各有至少 1 个成就、pokedex = 全部非元成就均已解锁。

存档 `achievements.json` 仅含 `{version, unlocked{}, stats}`（结构经 `python` 读取核实）；写前先落 `.bak` 回滚备份（`main.py:211-220`）。顶层 `achievements.json.bak` 残留文件存在。

## 5 验证情况

- 十二份拷贝的目录结构经 `ls -d` 核实，六主目录 + 六沙盒均存在。
- 主目录 / 沙盒同文件差异经逐棋种 `diff -q` 与 `grep -c "_pos_index"` 核实（结论见第 3.1、4 节）。
- 配置缓存各方法的行号与「`load_configs` 仅 `json.load`、无 schema 校验」均经直接阅读 `shared/game_base.py` 核实。
- 成就系统的两份硬编码副本、基线差分触发路径、`achievements.json` 结构与 `.bak` 残留均经阅读源码与读取文件核实。
- schema 校验确实不在 `load_configs` 中，而是出现在 AI 生成配置的「重试循环」里：生成结果经 `_hard_validate_config`（`shared/ai_orchestrator_base.py:1056`）做 schema 硬检查，失败则升温重试（`shared/ai_orchestrator_base.py` 约 2834 行处）。

运行时验证（例如实际跑一局并触发 AI 改规则后的缓存重载、或触发某成就解锁）在本次撰写中未执行，记为「未验证」。

## 6 局限性

- 十二份近乎逐字节重复的拷贝（`prompts.py` / `chess_ai.py` / `rule_engine.py`）是明显工程债。已抽出 `shared/mechanism_engine_base.py`，但 `prompts.py` / `chess_ai.py` / `rule_engine.py` / `main.py` 的其余重复尚未抽取。
- 立项简报称「`prompts.py`、`chess_ai.py` 两者逐字节相同」存在表述偏差：该结论对 xiangqi / weiqi / wuziqi / tiaoqi / heibaiqi 五组成立，但 dongwuqi 的主目录与沙盒版 `prompts.py` 与 `chess_ai.py` 均有实质差异（主目录版含「陷阱重构为地形棋子原语」特性，沙盒版缺省）。以代码为准，十二份拷贝并非全部两两一致。
- 立项简报把成就定义的位置写作 `xiangqi/main.py:148-195`，该引用有误：`ACHIEVEMENT_DEFINITIONS` 实际位于顶层 `main.py:148-195`，不在任一棋种子目录的 `main.py` 中；且条目数为 37 条（含 4 条元成就），而非简报所写的 35 条。
- 成就系统双份硬编码（Python 副本 + JS 副本），仅靠 `shared/achievement_checker.js:30` 的注释约束同步，无自动校验机制，两份副本字段也不完全一致（JS 副本无 `category / rarity / games`）。
- `load_configs` 不做 schema 校验，schema 校验只在 AI 生成配置后的重试循环里触发（`shared/ai_orchestrator_base.py:1056, ~2834`）。这意味着：若活配置 `configs/*.json` 被外部手段（非 AI 生成路径）改写成非法结构，缓存加载阶段不会拦截，错误会推迟到引擎使用配置时暴露。
- 沙盒主逻辑未接入 samsara 的 karma / skill 体系，导致「主目录进度语义」与「沙盒纯净语义」两套并存；二者对 `rule_engine` / `chess_ai` 的复用是同源的，但沙盒副本滞后于主目录的特性演进（如 dongwuqi 的地形棋子原语仅在主目录版存在）。
