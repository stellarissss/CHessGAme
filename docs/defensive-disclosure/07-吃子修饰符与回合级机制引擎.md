# 07 吃子修饰符与回合级机制引擎

## 摘要

本项目把「棋类规则」完全数据化，并允许玩家用自然语言指令实时改写规则。改写能力落在两个互不相干的层次上，必须先分清，否则无法理解后续文档对「业力」「识破」「机制原语」的描述：

- （A）**规则层修饰符**：由 `rule_engine` 解释，决定「某一颗子能不能走、能不能吃、能不能被吃、围棋某一块有多少气」。它改变的是着法集合本身，随 `rules.json` / `pieces_*.json` / `board_state.json` 持久化。
- （B）**回合级机制引擎**（`shared/mechanism_engine_base.py`）：不管「子怎么走」，只管「这一回合归谁走、走几步、是否跳过、是否由 AI 接管」。它改变的是回合流程，状态存在 `board_state["mechanisms"]`。

两者都由大语言模型经 JSON Patch 写入，但职责边界清晰。本分册给出两层的职责划分、原语定义，以及在本项目中的实现位置（均标注 `文件:行号`）。

## 1 背景与问题定义

玩家的自然语言指令经意图解析器分类（A 机制修改 / B 棋盘变换 / C 规则修改 / D 界面修改 / E 闲聊 / F 高级功能，见 `xiangqi/prompts.py:213-329`）。其中 C 类（改变走法、吃子规则、新建棋子）和 A2 子类（灵活编码机制修改）需要落到两套不同的数据通道：

1. C 类改动影响「某颗子能走到哪里、能吃掉谁」，属于规则层，由 `rule_engine` 在生成合法着法时解释。
2. A2 类中的 `add_mechanism`（跳过回合、AI 接管、随机走棋、额外回合、每回合多步、玩家控制）影响「这一回合怎么进行」，属于回合流程层，由 `mechanism_engine` 在执行回合前后解释。

问题定义：在「同一句自然语言 → 同一份 JSON Patch」的流程里，必须让「改走法」与「改回合流程」走两条互不污染的通道，且二者都可由数据持久化、即时生效，避免把回合控制逻辑混入着法生成逻辑，也避免把吃子能力写死在引擎里。

## 2 相关做法与本方案的区别

传统棋类引擎（如象棋的走法表、围棋的合法手生成）把「哪些着法合法」与「当前轮到谁」耦合在同一状态机里。本项目的区别在于：

- 着法生成（`rule_engine`）与回合流程（`mechanism_engine`）是两套独立模块，前者回答「这颗子能走哪」，后者回答「这回合归谁、走几步」。
- 着法生成采用数据驱动的解释器：走法以 `jump` / `ray` 两类基础定义描述，配合 `sym` 对称展开与 `where` 条件求值（`xiangqi/rule_engine.py:181 _expand_symmetry`、`:187 kind=="jump"`、`:218 kind=="ray"`、`:183 sym`、`:260/:297/:329 where`），因此「马走日」「象走田」这类规则是数据，不是代码分支。
- 回合控制同样数据化：`board_state["mechanisms"]` 是一组带 `remaining` 计数的原语列表，引擎只在回合边界读取它。

对比纯脚本化「跳过对方回合」的实现（通常是一行 `skip = True` 的标志位），本方案把六种回合效果抽象为可组合的、带剩余次数的原语，使 LLM 能用统一的 `add_mechanism` 动作描述任意回合级更改。

## 3 技术方案

### 3.1 规则层修饰符（吃子 / 气数）

规则层修饰符是附着在「棋子类型」或「棋子实例」上的字段，由 `rule_engine` 在生成着法或判定吃子时读取。

**象棋三类修饰器**（`xiangqi/rule_engine.py:101 resolve_modifiers`、`xiangqi/prompts.py:175-198 ATOMIC_CAPTURE_MODIFIERS`）：

- `can_capture`（默认 `true`）：设为 `false` 后，该棋子的合法着法中不再包含吃子着法（仍可走到空格）。
- `eatable`（默认 `true`）：设为 `false` 后，该棋子无法被吃（无敌）。
- `invulnerable`（默认 `false`）：`true` 等价于 `eatable: false`。

修饰器的有效值按四级优先级合并（低→高）：`rules` 全局类型映射 → `rules` 按阵营类型映射 → 阵营类型配置（`pieces_*.json` / `custom_pieces`）→ 棋子实例字段（`xiangqi/rule_engine.py:101-140`）。合并后对吃子着法的过滤由 `_restrict_captures` 完成：非吃子着法不受影响，仅当落点为敌方棋子时，须同时满足「进攻方 `can_capture` 为真」与「目标 `is_target_eatable` 为真」（`xiangqi/rule_engine.py:164-179`、`can_capture_piece` 见 `:158-162`、`is_target_eatable` 见 `:146-152`）。

**围棋专属修饰器**（`weiqi/rule_engine.py:287-322`、`weiqi/prompts.py:40-72 GO_RULE_PRIMER`）：

- `liberty_cap`：某色 / 某符号棋子连通块的气数上限，有效气数取 `min(实际气数, cap)`（`weiqi/rule_engine.py:305-322 _liberty_cap` / `_effective_liberties`）。
- `uncapturable`：某色 / 某符号不可被吃、不可断气，气尽也不提子（`weiqi/rule_engine.py:310-312 _uncapturable`）。

修饰器按颜色级与（可选的）符号级配置，符号级覆盖颜色级（`weiqi/rule_engine.py:292-303 _resolve_mods`）。这些都随 `rules.json → modifiers` 持久化，AI / 玩家修改后即时生效。

### 3.2 回合级机制引擎原语

`shared/mechanism_engine_base.py` 定义六个回合级原语，状态存于 `board_state["mechanisms"]` 下六个列表（`shared/mechanism_engine_base.py:98-106`）：

| 原语 | 含义 |
|:----:|:-----|
| `skip_turns` | 指定一方跳过若干回合 |
| `ai_control` | 指定一方若干回合由 AI 接管 |
| `random_moves` | 指定一方若干步随机走棋 |
| `extra_turns` | 指定一方连续多走若干回合 |
| `move_limits` | 指定一方每回合只能走若干步 |
| `player_control` | 改变默认由玩家控制的一方 |

生命周期分两阶段：`apply_pre_turn_mechanisms`（回合开始前，`:117-159`）处理跳过、AI 接管、初始化 `move_limits` 的 `remaining_moves`；`apply_post_move_mechanisms`（走棋后，`:165-229`）处理随机走棋消耗、步数限制、额外回合、AI 接管次数消耗。每个原语条目带 `remaining` 计数，正数表示剩余次数，每被触发一次递减，归 0 即从列表 `pop`；`remaining < 0` 表示无限（`_find_active_mechanism`，`:411-418`，判定条件为 `remaining != 0`）。

### 3.3 两层职责边界

- **`rule_engine`**：数据驱动的着法解释器。输入棋子定义（`jump`/`ray` + `sym` + `where`）与修饰器，输出合法着法集合。它不关心「轮到谁」。
- **`mechanism_engine`**：回合流程控制器。输入 `board_state["mechanisms"]`，输出「本回合是否跳过、是否 AI 控制、是否额外回合、剩余步数」等流程信号。它不生成着法。
- **配置来源差异**：`mechanism_engine` 的 `rules_config` 仅用于读取 `ai_difficulty.personality`（`shared/mechanism_engine_base.py:325-339`），机制状态本身不在 `rules.json`，而在 `board_state["mechanisms"]` 并随 `board_state.json` 持久化。

## 4 本项目实现

- 规则层修饰符的合并与吃子过滤：`xiangqi/rule_engine.py:101-179`；提示词定义 `xiangqi/prompts.py:175-198`。
- 围棋气数 / 不可吃修饰器：`weiqi/rule_engine.py:287-322`；提示词定义 `weiqi/prompts.py:40-72`。
- 回合级引擎基类与六原语：`shared/mechanism_engine_base.py:98-106`，生命周期 `:117-159` 与 `:165-229`，无限机制判定 `:411-418`。
- 机制由 LLM 写入：意图解析器 A2 子类 `add_mechanism`，`mechanism_type` 枚举见 `xiangqi/prompts.py:238`，目标文件为 `["board_state.json","rules.json"]`（`xiangqi/prompts.py:316`）。
- AI 性格映射：`rules.json` 的 `personality` 预设 `normal` / `aggressive` / `defensive` / `random` 加 `custom`，映射到 `depth_mult` 与 `randomness_mult`（`shared/mechanism_engine_base.py:346-405`）。
- 工程事实：该基类模块头部注释自述是从十二份 `mechanism_engine.py`（顶层六棋类 + sandbox 六副本）经 difflib 量化抽取的公共基类，其中顶层六份平均相似度 96.4%、sandbox 副本与顶层同名文件 100% 相同（`shared/mechanism_engine_base.py:5-10`）。

## 5 验证情况

- 修饰符合并的优先级、吃子过滤逻辑、围棋限气 / 不可吃逻辑，均已对照源码复核（见第 4 节行号）。
- 六原语与生命周期、无限机制判定，均已对照源码复核。
- 本分册未运行项目做端到端实测；机制的实际运行时行为（如 `skip_turns` 与 `extra_turns` 在边缘情形下的交互）**未验证**，建议后续以单元测试用例覆盖。

## 6 局限性

- 两层机制都依赖 LLM 正确产出 JSON Patch。若 LLM 把本应写入 `board_state["mechanisms"]` 的回合控制误写入 `rules.json` 的修饰器字段（或反之），会导致语义错位。该风险由提示词中的目标文件映射（`xiangqi/prompts.py:316`）约束，但无编译期校验。
- `rule_engine` 的修饰器与 `mechanism_engine` 的状态分处不同文件（`rules.json` / `pieces_*.json` 与 `board_state.json`），二者一致性依赖人工同步，是已知工程风险。
- `where` 条件求值、对称展开等数据驱动逻辑的表达力上限，未在本分册范围内量化。
